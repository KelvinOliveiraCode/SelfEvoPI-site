How it adapts

The core runs a continuous loop. Each stage is independently testable and injectable.

  1. detectPoints to a repeated failure, a missing capability, or a fragile flow.
  2. specifyWrites a short contract with inputs, outputs, bans, and test cases.
  3. generateProduces the lightest artifact and runs node --check before writing.
  4. verifyProbes the real interface for that artifact kind.
  5. gateCompares with the baseline and requires zero regressions.
  6. promote or revertCommits atomically with memory, or rolls back and revalidates.

Architecture

A thin layer around the engine. No fork, no bundled dependencies, no required container.

  • CLIThe REPL, palette, markdown, activity lines, and overlays.
  • RPC clientThe single point of contact with the engine protocol.
  • RouterProfiles, circuit breaker, retry, and a token ceiling.
  • EvalsDeterministic tasks, checkers, and a regression gate.
  • MemorySession, project, and skills, pruned by evidence.
  • SandboxStatic gate, Permission Model, process containment.
  • GovernanceVerified rollback and specific human approval.
  • GraphA validated graph with checkpoint, pause, and resume.

The probe decides the artifact

  • MCP configvalid JSON and keys
  • skillexists and describes the capability
  • CLIprobes the contract flags
  • extensionimports with a mocked host
  • MCP serverJSON-RPC 2.0 over stdio

The verifier runs outside the sandbox and the artifact inside a temporary directory. A smoke test that always passes is not evidence.

Guarantees around the loop

  • Static gate masks comments and literals before analysis
  • Permission Model with no network or child process
  • Tree kill reaches detached grandchildren on timeout
  • Memory promotes from session to project to skills
  • Rollback that fails never updates last known good
  • Graph checkpoints bind each node to a git commit

What sets SelfEvoPI apart

It measures before promotingDeterministic evals compare each task with a baseline. Promotion requires the target task to pass with zero regressions.
It writes the missing capabilityThe core detects a gap, writes the lightest artifact, probes its real interface and promotes only when the gate is green.
It routes with a budgetProfiles, circuit breaker, retry and a token ceiling decide which provider and model run each task.
It contains what it runsA static gate, the Node permission model, process-tree containment and protected areas surround generated code on Windows.
It leaves an audit trailBlock and warn decisions go to a local ledger with redacted excerpts, readable without exposing secrets.
It runs hooks without a shellLifecycle hooks read JSON from stdin, have a timeout and a minimal environment, and never call a shell.

Other harnesses

Claude Code

CLI, IDE, desktop, web and mobile over one engine. Anthropic models with third-party providers on some surfaces. Auto memory, /resume with search, /fork, /rewind and /goal with a separate evaluator. Six named permission modes, MCP, skills and plugins. No primary source says it modifies its own code.

SelfEvoPI adds a baseline regression gate and a core that writes and verifies artifacts. No primary source says Claude Code rewrites its own harness.

OpenCode

The most model-agnostic of the group: TUI, desktop and web through opencode pair. MCP, plugins, skills and agents in Markdown files. /sessions, /fork, /compact and background subagents. No named approval modes; security is allow, ask and deny rules per agent. No /goal or /loop confirmed in the inventory of 34 commands.

SelfEvoPI adds deterministic evals with a regression gate, a native Windows sandbox and a redacted security ledger.

Codex CLI

OpenAI models across CLI, desktop, web and cloud. MCP, skills, subagents and /goal tied to a verifiable condition. It separates sandbox reach from the moment of asking, with automatic approval review. Four named interface modes and /permissions in the CLI.

SelfEvoPI adds an engine-agnostic router with profiles, circuit breaker and a token ceiling. The sources consulted tie Codex to OpenAI models.

Hermes Agent

Model-agnostic across CLI, desktop and messaging gateways. Memory in MEMORY.md and USER.md with FTS5 search over past conversations. Over 40 tools, MCP, skills, plugins and subagents. Declared self-evolution: it creates and improves skills and runs background review. /goal uses an auxiliary Ralph-loop judge. Eight documented security layers.

SelfEvoPI adds a baseline comparison before promotion and probes of the real artifact interface. Both evolve, but the sources describe different gates.

DeepSeek Harness

Everything is a plugin over Cordis: model, tools and agent loop are replaceable by configuration. Web UI, Desktop, CLI, SDK and ACP. Append-only session log with fork and resume. ctx.goals is same-session; no evidence of self-evolution, long-term memory, MCP, REPL or named skills. SAFETY.md calls it a developer preview with no audit and says sandboxing does not guarantee isolation.

SelfEvoPI adds verified rollback, a static gate and memory that persists across sessions. DeepSeek documents same-session goals only.

Unharnessed

One tool: a persistent Python REPL. The model writes the rest. No declared memory, no permission prompts, no subagents. Goal mode ends only with goal.complete(), with a budget that degrades and gates run by the harness. The README warns that the kernel is not a sandbox. The 47 of 66 claim is not verifiable because the benchmark section shows Placeholder data.

SelfEvoPI adds the structure Unharnessed leaves out: router, evals, memory, sandbox and governance. The tradeoff is deliberate, not a defect.

PI Coding Agent

A minimal and extensible harness. Five interfaces: TUI, print, JSON, RPC and SDK. Model-agnostic through pi-ai. Session tree, native MCP, skills as /skill:name, custom keybindings and RPC. The README says it deliberately skips subagents and plan mode and includes no permission system, so it runs with the permissions of the user who launched it.

SelfEvoPI adds a built-in permission system, a native sandbox and a regression gate. The Pi README says it omits a permission system and subagents by design.

SelfEvoPI bets that the right amount of structure wins.

Unharnessed bets that less structure wins. The 47 of 66 tasks claim on its site is unverified: the benchmark section shows Placeholder data.

Security and limits

What exists

  • Static gate, 13 rules, Permission Model, process containment
  • evals/ and core/governance/ stay protected
  • Network, credentials, and outside writes pause for approval
  • No secret is printed, logged, or committed
  • Lifecycle hooks read JSON, never call a shell

What does not exist

  • Lexical skills, no embeddings
  • Clock and ledger trigger, no external sources
  • Four models end calls without text
  • No /btw, custom keybindings, or title progress bar
  • Cells use internal tools, no full gateway wiring
  • Real LSP server and real DAP process remain unproven

Install

The repository is the current path. Four commands take a clean checkout to a running CLI.

git clone <repo-url> SelfEvoPI
cd SelfEvoPI
npm run verify
npm run cli

Requirements

Windows, nativeNo Docker, WSL or virtual machine.
Node 22.19.1 or newerThe version floor the harness is measured against.
Git 2.55 or newerWith core.longpaths set to true.
The engine CLIInstalled separately. SelfEvoPI speaks to it over RPC and does not fork it.

npm run verify is what CI runs. It is green on this checkout: exit 0 and 33 of 33 source URLs returning 200.

CLI surface

One surface: a conversation with a command palette. Modes change what the harness may do with the workspace. Commands change what it knows and shows.

Modes

planbuildmanualaskgoal
  • /planReads and proposes. It does not write.
  • /buildWrites and runs inside the workspace.
  • /manualBuild with a confirmation before each write.
  • /askAnswers only. It never touches disk.
  • /goal <condição>Adds a completion check that clears itself once satisfied.

Permission and approver are separate axes from mode, and the status line shows them separately.

In prose, ultrathink raises effort, chillax lowers it, and orchestrate or workflowz set the task role. No code or path changes.

Teams, events and memory

Version 2.0.0 keeps state between turns without adding a dependency.

Persistent teamsA board, messages and a deterministic step survive a restart. Writes are atomic.
Local event busEvents are deduplicated and keep a saved cursor, so a restart does not replay them.
Automatic memoryFacts are redacted before storage and recalled by term overlap.
Persistent cellsA restricted runtime keeps state between calls. Calls and output have fixed limits.
Agent definitionsFrontmatter files define modes and ordered permission rules.
Refutation auditA claim is tested against the running CLI before it stays in the foundation document.

Hooks & Code Mode

Two opt-in layers sit between the harness and the work: lifecycle hooks that observe a turn, and a code mode that replaces a large tool catalog with one call.

Hooks

Workspaces declare lifecycle hooks in .pi/hooks.json, workspace-local and never your personal agent config. /hooks shows the configuration and the last results.

  • turn_start
  • turn_end
  • tool_start
  • tool_result
  • error
  • compact
  • stdinEach hook receives the event as JSON.
  • shellNever called. Hooks run without one.
  • timeoutEvery hook has one, so a slow hook is stopped.
  • environmentMinimal, by design.
  • failureRecorded, never fatal to the turn.

Code Mode

In a workspace with many MCP servers the tool catalog can flood the context. Opt-in code mode runs a short JavaScript program in a restricted node:vm context whose only effect is tools.call(name, args).

  • node:vmA restricted context, not the main one.
  • tools.callThe only way to reach a tool.
  • blockedNo process, require, fetch, eval or Function.
  • limitsAllowlist, call limit, deadline and output cap.

The gateway is opt-in and registered locally by the user. It discovers servers and tools from the local config at runtime, so no server name, command or credential lives in the repository.
